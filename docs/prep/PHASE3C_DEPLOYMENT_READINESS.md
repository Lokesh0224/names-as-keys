# Stage 3C deployment-readiness reads

This checklist is a review requirement, not a deployment script or transaction authorization. All current fork proofs concern Sepolia block 12071220 only. No checklist item below implies that a live project root/R1/R2/registrar exists. Live deployment remains BLOCKED until reproducible source-to-bytecode verification is completed and reviewed, owner/guest account checks pass, the ENS role inventory and permission checks below pass, concrete addresses and fresh chain observations are verified, and the owner explicitly authorizes the exact transactions. Interface signatures, implementation addresses, runtime hashes and passing fork tests do not substitute for the source-to-bytecode verification gate.

## Before any intended root registration

Use a credential-safe provider and one identified block for dependent reads; record number/hash and chain ID. Read-only calls must succeed, not merely return transport HTTP 200.

- `eth_chainId == 11155111`; `eth_getBlockByNumber(block,false)` matches the recorded block/hash. `eth_getBalance(owner,block)` covers a separately estimated transaction budget. MetaMask's selected public account must match the intended owner; no recovery material is needed.
- `eth_getCode(address,block)` must be nonempty for every consumed manifest contract. Hash bytecode with Keccak-256 and compare with the reviewed runtime identities in `evidence/stage3c/pinned-chain.json`; reject unexplained drift. Matching bytecode hashes establish equality to that recorded runtime, not to a reproducible source build.
- `RootRegistry.getSubregistry("eth") == ETHRegistry`. Use manifest registrar `0xf633e7fc17e2bbe0d0965d18ec1821dcb754a3d3` and ETHRegistry `0xd4ebcbbdf463c9c45784603db0ddd499bc44a8b4` on Sepolia only. Cross-check fresh official deployment references before future writes.
- `ETHRegistrar.isAvailable("nak-lokesh-20261105") == true`; `ETHRegistry.getState(labelhash)` must be consistent with current availability. `isAvailable` is authoritative for registrar/grace constraints; `AVAILABLE` status alone is insufficient. No synthetic fixture proves live availability or owner control.
- `MIN_REGISTER_DURATION()`, `MIN_COMMITMENT_AGE()`, `MAX_COMMITMENT_AGE()` must be read from the deployed registrar, with duration/wait-window inputs matching those values. The existing fork tests exercise these actual getter signatures.
- `getRegisterPrice(label,duration,paymentToken)` must succeed for the selected token. Token `decimals()`, `balanceOf(payer)` and `allowance(payer,ETHRegistrar)` must support the fresh quoted spend. Zero ETH call value is not zero gas cost. Mock mint/approval, commitment and registration are future explicitly authorized transactions.
- `makeCommitment(...)` must match the exact owner, label, CSPRNG-generated registration secret, registry/resolver, duration and referrer. After a future authorized commitment, read `commitmentAt(commitment)` and current block timestamp; check minimum age ≤ age < maximum age before reveal. These reads do not authorize committing or revealing.

## Before registrar deployment/configuration or credential issuance

Concrete R1/R2 must have been deployed and attached by separately authorized transactions. The intended root cannot be assumed to exist from this repository's tests.

1. Chain/block checks above pass. `Factory.verifyContract(R1)` and `verifyContract(R2)` both return reviewed UserRegistryImpl `0x9bd8a88719068d09ecee662f36c0e3856708366a`. Independently read and hash implementation, factory and relevant proxy runtime code. A matching implementation address is separate from runtime identity and source equivalence. No empty/failed verification result is acceptable.
2. `ETHRegistry.getState(rootLabelHash)` and `R1.getState(lockLabelHash)` both return REGISTERED, expiry > block timestamp, and their token IDs match the registrar's immutable snapshots. `getOwner(...)` at each level equals the registrar's configured owner. Lock expiry ≤ root expiry. Record `getResource(...)` as a distinct value; it is not an ERC-1155 token ID and can change at expiry without a new registration.
3. `ETHRegistry.getSubregistry(rootLabel) == R1` and `R1.getSubregistry("lock") == R2`. `RootRegistry.getSubregistry("eth") == ETHRegistry`. `R1.getParent()` and `R2.getParent()` should match canonical metadata, but metadata alone is not forward attachment authorization.
4. Read registrar getters `owner()`, `rootLabel()`, `rootTokenId()`, `lockTokenId()`, `parentRegistry()`, `guestRegistry()` and verify the intended configuration and bytecode. Before deployment these are constructor inputs and readbacks from ENS; after deployment they are mandatory readbacks. The old configured owner retains cleanup authority in fixed R2 even if ancestors later change.
5. `R2.ROOT_RESOURCE()` gives the resource for the following reads. `R2.roles(rootResource,registrar) == 4097` exactly; `R2.hasRootRoles(1,registrar)` and `hasRootRoles(4096,registrar)` are true; `R2.isEmancipated() == false`. Registrar roles must contain no admin, RENEW or UPGRADE bits. Removing REGISTRAR blocks new issuance but does not remove emergency revocation; removing UNREGISTER blocks revocation through this registrar.
6. Inventory trusted administrators and their actual roles using `roles(rootResource,account)`, `roleCount(rootResource)` and `getAssigneeCount(rootResource,roleBitmap)`. EAC exposes no complete account enumeration getter: reconstruct known assignees from the complete deployment-to-current `EACRolesChanged` event history, then confirm each current bitmap and aggregate counts. **An incomplete inventory is a readiness blocker.** Identify holders of UNREGISTER_ADMIN, REGISTRAR_ADMIN, REGISTER_RESERVED(_ADMIN), RENEW(_ADMIN), and UPGRADE(_ADMIN). Their powers are not controlled by the registrar. The selected owner-revocable profile must not delegate root administration to guests/operators.
7. `R2.roles(rootResource,guest) == 0`; guest is nonzero, different from owner and registrar. Guest smart-contract receiver behavior requires review. Operator approval can be present; it is not itself a transfer or issuance permission.
8. `R2.getState(guestLabelHash)` must have AVAILABLE status, expiry zero, latestOwner zero, token ID `LibLabel.withVersion(labelhash,0)` and resource `LibLabel.withVersion(labelhash,1)`. This is the tested initial-state predicate. It proves no recorded use under the inspected implementation/current state, not permanent historical uniqueness across administrator/implementation/registry changes.
9. Absolute expiry is at least timestamp+60 seconds, at most timestamp+30 days and no later than the validated lock/root expiries. Inputs must pass the registrar's 3–32-character lower-case ASCII label policy. Repeat time-sensitive reads and transaction simulation immediately before requesting a future MetaMask signature.
10. Prepare exact recipient/function/calldata, ETH value, token spend, `eth_estimateGas` results and fees, expected MetaMask approvals and failure/retry policy. Live deployment remains BLOCKED pending completion and review of reproducible source-to-bytecode verification, owner/guest account confirmation and the ENS role checks above, followed by explicit transaction approval. Interface/address/runtime checks do not complete the source-to-bytecode gate.

## Before active revocation; expired-token policy

- `Factory.verifyContract(R2)` still reports the expected implementation, and runtime identities remain reviewed.
- Registrar caller equals configured owner. `R2.getState(labelhash)` is REGISTERED with expiry > now and exact token ID matching the owner's revocation request. `R2.hasRootRoles(4096,registrar)` is true. An exact 4097 bitmap is required for issuance, while UNREGISTER alone is sufficient for active cleanup.
- Do not require active ancestors for fixed-R2 cleanup: detachment/ancestor expiry blocks issuance but need not block withdrawing an existing active credential from original R2.
- Expired tokens are AVAILABLE and `getOwner`/`ownerOf` return zero, although `latestOwner` can retain the guest. They need no explicit cleanup to fail the current-state access predicate. `unregister` rejects them; this registrar deliberately neither renews nor exposes expired-token cleanup.
- Root RENEW can revive an expired, unburned credential with the same token ID and owner. That can restore current-state access if ancestors/attachments are valid. Preventing this requires an additional reviewed administration/implementation policy; removing only operational RENEW is insufficient if RENEW_ADMIN remains.
- Optional destruction of an expired residual token requires privileged renewal followed immediately by unregister in **one atomic administrative transaction**, with expected-token checks. The test-only `AtomicExpiredCleanupProbe` demonstrates this sequence. It is not production code or an approved workflow. Separate MetaMask renewal and unregister transactions create a revival window and are not the selected cleanup policy. Burned-token renewal produces RESERVED rather than guest ownership; authorized later re-registration remains possible.

## Actions that break or exceed the guarantee

An administrator can remove registrar UNREGISTER, remove all owner recovery powers, grant destructive root admin permissions to a guest/operator, or change R2 implementation so verification fails. These defeat or block active revocation. RENEW can restore naturally expired unburned credentials; REGISTRAR/REGISTER_RESERVED powers can reissue names directly, bypassing registrar no-reuse policy. A malicious/compromised owner, loss of signing control, incompatible registry upgrades and reverting ENS dependencies are outside the conditional guarantee. Root/lock transfer or detachment denies new issuance but does not itself remove original-R2 revocation rights. No independent access or revocation database is proposed.
