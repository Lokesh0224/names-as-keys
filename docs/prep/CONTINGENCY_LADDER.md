# Demo contingency ladder

The ladder order is a **PROPOSAL**; each rung must be clearly disclosed as live, forked, or prerecorded.

1. **Live Sepolia E2E:** owner grants guest access, guest uses the mobile HTTPS flow, and the simulated door reacts to an observed event. Use only after kickoff and applicable live-action authorization.
2. **Local Anvil Sepolia fork:** run the forked setup and demo with local state. State clearly that transactions/state are local fork simulation and not live Sepolia.
3. **Pre-recorded video:** play a recording of a verified flow if live and forked demos are unavailable. Label what is recorded and whether it is live/forked; do not imply current live chain state.

**Record the moment anything works.** Record raw screen/video evidence before changing the working environment, then save a copy in the approved submission location.

## Recording checklist — PROPOSAL

- Show the environment label (live Sepolia / local Anvil fork / recorded run).
- Show owner grant, guest wallet result, and simulated door response in sequence.
- Keep secrets, seed phrases, private keys, RPC credentials, and wallet recovery screens off camera.
- Include visible pending/success/failure behavior and avoid editing out a material failure while presenting it as success.
- Capture a backup copy and note the date, chain/environment, and code version; live external facts remain HUMAN TO CONFIRM.
