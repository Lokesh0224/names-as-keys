## S2. Transfer entry points and gates

**VERIFIED ARTIFACT.** The safe ERC-1155 entry points are inherited from upstream `contracts/src/erc1155/ERC1155Singleton.sol`: `safeTransferFrom` calls `_safeTransferFrom` (`contracts/src/erc1155/ERC1155Singleton.sol:79-85`) and `safeBatchTransferFrom` calls `_safeBatchTransferFrom` (`contracts/src/erc1155/ERC1155Singleton.sol:95-107`); those internal paths call `_updateWithAcceptanceCheck` with `safe=true` (`contracts/src/erc1155/ERC1155Singleton.sol:258-270`, `contracts/src/erc1155/ERC1155Singleton.sol:282-294`). UserRegistry inherits these through PermissionedRegistry (`contracts/src/registry/PermissionedRegistry.sol:59`; `contracts/src/registry/UserRegistry.sol:22-27`).

PermissionedRegistry adds `unsafeTransfer` (`contracts/src/registry/PermissionedRegistry.sol:168-174`) and `unsafeBatchTransfer` (`contracts/src/registry/PermissionedRegistry.sol:175-190`). They call the same update machinery with `safe=false`. The complete token update override is `contracts/src/registry/PermissionedRegistry.sol:477-508`:

- On a real transfer (`from` and `to` nonzero), safe paths first revert `TransferUnsafeUntilRegistryIsEmancipated` when `isEmancipated()` is false (`contracts/src/registry/PermissionedRegistry.sol:489-493`). This check precedes the transfer-role loop.
- Each token then checks `ROLE_CAN_TRANSFER_ADMIN` against `_getRoles(resource, from)` (`contracts/src/registry/PermissionedRegistry.sol:494-500`). The source comments state this is checked on the original owner, is a token property, and is ignored on root (`contracts/src/registry/PermissionedRegistry.sol:497-499`). Thus the transfer gate is the token resource's original-owner role, not root or an OR of root and token roles.
- Safe paths additionally require the sender to be the only assignee of all roles on that token (`contracts/src/registry/PermissionedRegistry.sol:501-502`). A successful positive-amount transfer moves the token resource roles from `from` to `to` (`contracts/src/registry/PermissionedRegistry.sol:503-504`).
- Batch transfer iterates each token ID through the same checks (`contracts/src/registry/PermissionedRegistry.sol:494-505`). The unsafe batch entry point chooses the first token's owner and makes unit amounts (`contracts/src/registry/PermissionedRegistry.sol:176-189`); a meaningful test must use a nonempty batch of IDs owned by the same `from`.
- Mint and burn are not token transfers for this gate: the override applies these gates only when both endpoints are nonzero (`contracts/src/registry/PermissionedRegistry.sol:489-490`). `setApprovalForAll` is approval setup, not a transfer entry point (`contracts/src/erc1155/ERC1155Singleton.sol:65-67`).

The base ERC-1155 entry points also require valid owner/operator approval before update (`contracts/src/erc1155/ERC1155Singleton.sol:79-85`, `contracts/src/erc1155/ERC1155Singleton.sol:95-107`; unsafe variants `contracts/src/registry/PermissionedRegistry.sol:171-184`). Matrix outcomes below assume valid token ownership, required approval, a nonzero receiver, and valid amounts/array lengths.

## S3. Emancipation and supplied root-role setup

**VERIFIED ARTIFACT.** `PermissionedRegistry.isEmancipated()` returns true exactly when `UNEMANCIPATED_ROLE_BITMAP` has no intersection with the role bitmap reconstructed from `roleCount(ROOT_RESOURCE)` (`contracts/src/registry/PermissionedRegistry.sol:395-401`). `EACBaseRolesLib.fromCounts` reconstructs the set of roles with nonzero counts (`contracts/src/ens-vendored/access-control/libraries/EACBaseRolesLib.sol:36-41`).

The forbidden root roles are `ROLE_SET_SUBREGISTRY`, its admin, `ROLE_SET_RESOLVER`, its admin, `ROLE_UNREGISTER`, its admin, `ROLE_UPGRADE`, and its admin (`contracts/src/ens-vendored/registry/libraries/RegistryRolesLib.sol:65-75`). `ROLE_RENEW` and `ROLE_RENEW_ADMIN` are explicitly excluded (`contracts/src/ens-vendored/registry/libraries/RegistryRolesLib.sol:65-66`, `contracts/src/ens-vendored/registry/libraries/RegistryRolesLib.sol:28-31`).

**USER-REPORTED:** setup has an owner with full root roles including admins and a registrar grant bitmap of decimal `4097`. **INFERENCE:** if those reported grants are present at root, `isEmancipated()` returns false because the owner's prohibited roles are counted; independently, `4097 = 1 + 4096`, i.e. `ROLE_REGISTRAR | ROLE_UNREGISTER` (`contracts/src/ens-vendored/registry/libraries/RegistryRolesLib.sol:8-11`, `contracts/src/ens-vendored/registry/libraries/RegistryRolesLib.sol:23-26`), so a root assignment of `4097` itself includes a prohibited role. This setup and result were not read from chain in this continuation.

To make the predicate true, all root assignees of every role in the forbidden bitmap must have those assignments revoked so the corresponding root role counts become zero. This is role revocation, not burning ERC-1155 tokens. `revokeRootRoles` is the public root revocation function and is admin-gated (`contracts/src/ens-vendored/access-control/interfaces/IEnhancedAccessControl.sol:85-89`; upstream `contracts/src/access-control/EnhancedAccessControl.sol:145-153`). Non-forbidden root roles may remain; for example, `ROLE_REGISTRAR` is not in the forbidden bitmap. Whether that state is reachable in a particular deployed instance depends on its current role assignees and authorization, which are **NOT OBSERVED** here.

## S4. Grant/revoke mechanics for transfer permission

`grantRoles(anyId, ...)` and `revokeRoles(anyId, ...)` in PermissionedRegistry map `anyId` to the canonical token resource (`contracts/src/registry/PermissionedRegistry.sol:240-255`). EAC requires the relevant admin authority for grants and revocations (`contracts/src/access-control/EnhancedAccessControl.sol:107-153`, `contracts/src/access-control/EnhancedAccessControl.sol:365-417`); its effective-role calculation combines root and resource roles (`contracts/src/access-control/EnhancedAccessControl.sol:427-430`).

Registry-specific grant filtering matters: token-resource `_getSettableRoles` returns only the lower 128-bit regular-role portion (`contracts/src/registry/PermissionedRegistry.sol:548-575`), and its comments state token admin roles are assigned only during registration (`contracts/src/registry/PermissionedRegistry.sol:551-558`). `ROLE_CAN_TRANSFER_ADMIN` is an upper-half admin role (bit 156) (`contracts/src/ens-vendored/registry/libraries/RegistryRolesLib.sol:43-45`). Therefore it cannot be granted later through token-resource `grantRoles`, including by a root-role holder. An owner with an empty bitmap and no applicable root admin role also cannot self-grant token roles; grants require admin authority and registry filtering (`contracts/src/access-control/EnhancedAccessControl.sol:107-119`, `contracts/src/access-control/EnhancedAccessControl.sol:365-402`; `contracts/src/registry/PermissionedRegistry.sol:563-575`). If the token owner itself also holds root admin roles, those can authorize regular-role grants, but the token admin-role filter still prevents granting `ROLE_CAN_TRANSFER_ADMIN` after registration (**INFERENCE** from those source rules).

Revocation differs: EAC's default revokable set is derived from effective root plus resource roles and includes admin roles (`contracts/src/access-control/EnhancedAccessControl.sol:376-417`, `contracts/src/access-control/EnhancedAccessControl.sol:427-430`). Consequently, a parent/root-role holder can revoke a child's `ROLE_CAN_TRANSFER_ADMIN` only if that caller has the corresponding admin authority in the effective roles; a generic unrelated root role is insufficient. The public route is `revokeRoles(anyId, roleBitmap, account)` (`contracts/src/registry/PermissionedRegistry.sol:248-255`). A role-change callback regenerates the token by burn-and-mint while retaining the resource (`contracts/src/registry/PermissionedRegistry.sol:522-545`). The exact caller's authority and current role assignments are **NOT OBSERVED**.

## S6. Owner, expiry, state, and access observations

`getExpiry(anyId)` returns the registry entry expiry (`07e55a056f5b6a9c90119f501bdd05714e67dddd/contracts/src/registry/PermissionedRegistry.sol:307-310`). `getOwner(anyId)` returns zero if expired; otherwise it resolves the current token ID and ERC-1155 owner (`contracts/src/registry/PermissionedRegistry.sol:320-323`). `getState(anyId)` returns expiry, current token ID/resource, `latestOwner` from the underlying owner mapping, and status (`contracts/src/registry/PermissionedRegistry.sol:330-341`). These are state views, not access-control checks. A transfer updates the ERC-1155 owner and moves that resource's roles to the recipient (`contracts/src/registry/PermissionedRegistry.sol:494-505`; EAC role move implementation `contracts/src/access-control/EnhancedAccessControl.sol:205-231`).

Other access paths exist in the source: EAC role checks combine root and resource roles (`contracts/src/access-control/EnhancedAccessControl.sol:427-430`); the registry's role lookup can include a token owner's roles for an approved-for-all operator (`contracts/src/registry/PermissionedRegistry.sol:576-590`). These source paths describe authorization mechanics; they do not establish any particular account's current access or constitute a mitigation. No runtime state was inspected.
